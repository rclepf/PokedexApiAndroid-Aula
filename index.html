Arquitetura MVVM: Cada Coisa no Seu Lugar

O problema que a arquitetura resolve

Imagine um app onde a Activity faz tudo: abre a conexão de rede, converte o JSON, guarda os dados numa variável, trata o erro, atualiza a tela e ainda controla a animação de carregamento. No começo funciona. O problema aparece depois:

  • O arquivo cresce sem parar. Telas reais chegam a 800, 1.500 linhas num único arquivo. Achar um bug vira arqueologia.
  • Nada pode ser testado isoladamente. Para testar se o cálculo de um desconto está certo, você precisaria abrir a tela inteira num emulador — porque a regra de negócio está grudada no código visual.
  • Duas pessoas não conseguem trabalhar na mesma tela. Se tudo está num arquivo só, dois desenvolvedores editando a mesma tela geram conflito a cada commit.
  • Trocar qualquer coisa quebra o resto. Mudar de uma API para outra obrigaria a mexer no arquivo da tela — que não deveria nem saber que existe uma API.

Esse padrão tem até apelido no mercado: God Activity (a "Activity Deus", que sabe e faz tudo). Arquitetura é, basicamente, o conjunto de regras que impede isso de acontecer.

A evolução: de MVC a MVVM

O Android não chegou ao MVVM de primeira. A comunidade passou por outros padrões, e entender por que cada um foi substituído ajuda a enxergar o que o MVVM está resolvendo:

PadrãoComo funcionaLimitação no Android
MVC
Model-View-Controller		 Um Controller recebe as ações do usuário e atualiza o Model e a View. No Android, a Activity acabava sendo View e Controller ao mesmo tempo — o que recria a God Activity.
MVP
Model-View-Presenter		 Um Presenter comanda a View por meio de uma interface (mostrarCarregando(), exibirLista()...). Funciona, mas gera muito código repetitivo, e o Presenter guarda uma referência direta à View — o que causa vazamento de memória se a tela for destruída.
MVVM
Model-View-ViewModel		 O ViewModel expõe um estado. A View observa esse estado e se redesenha sozinha quando ele muda. É o padrão recomendado hoje: o ViewModel não conhece a View, sobrevive à rotação e se encaixa naturalmente no Compose.
A diferença essencial entre MVP e MVVM: no MVP, o Presenter manda a tela fazer coisas ("mostre o loading agora"). No MVVM, o ViewModel apenas declara como as coisas estão ("o estado é Loading") e a tela reage. Isso inverte a dependência: o ViewModel deixa de conhecer a tela, e por isso pode ser testado sem nenhuma tela existir.

As três camadas, no nosso projeto

CamadaResponsabilidadeNo nosso projeto
ModelRepresenta os dados e como obtê-los. Não sabe nada sobre telas.pacotes model e network
ViewModelO cérebro da tela: pede os dados, guarda o estado atual, expõe para a UI.pacote viewmodel
ViewSó desenha o que o ViewModel mandou. Camada passiva.pacote ui
Um teste rápido para saber se a separação está correta: percorra os import de cada arquivo. Se a tela importa algo de network, a separação foi quebrada. Se o ViewModel importa algo de androidx.compose.ui (fora do mutableStateOf), também. Cada camada deve depender apenas da que está imediatamente "abaixo" dela.

A regra que mantém tudo previsível: o estado desce, o evento sobe. A tela nunca altera dados por conta própria — ela apenas avisa o ViewModel que algo aconteceu.

Por que o ViewModel sobrevive à rotação da tela

Quando o celular gira, a Activity é destruída e recriada do zero — é assim que o Android sempre funcionou, para poder recarregar recursos diferentes. Se o estado da tela morasse dentro da Activity, ele se perderia a cada rotação.

O ViewModel escapa disso porque não pertence à Activity: ele pertence a um objeto interno chamado ViewModelStore, que o sistema mantém vivo durante uma mudança de configuração (rotação, idioma, modo escuro) e só destrói de vez quando a tela é fechada por completo. Por isso, ao girar o aparelho, o Pokémon que já estava carregado continua na tela — sem uma nova chamada de rede.

Teste na prática: depois que o app estiver rodando, gire o emulador (Ctrl+F11). Se o Pokémon não recarregar do zero, é a prova visual de que o ViewModel sobreviveu.

O que você ganha na prática com essa separação

VantagemComo se manifesta no dia a dia
Testabilidade O PokedexViewModel é uma classe Kotlin comum, sem nada de visual. Dá para testar a lógica de busca e de navegação Prev/Next sem abrir um emulador — testes que rodam em segundos, não minutos.
Trocar peças sem quebrar o resto Se a PokéAPI mudasse de endereço ou fosse substituída, só o pacote network mudaria. A tela e o ViewModel continuariam intactos.
Trabalho em paralelo Com camadas separadas em arquivos distintos, uma pessoa pode cuidar da tela enquanto outra ajusta a camada de dados — sem conflito no Git.
Sobrevivência a mudanças de configuração Rotação, troca para modo escuro ou mudança de idioma não descartam os dados já carregados, porque eles não moram na tela.
Onboarding mais rápido Quem entra no projeto depois sabe onde procurar: erro de rede está em network, comportamento de tela está em viewmodel. Não precisa ler o projeto inteiro.

Onde isso está no mercado

Este não é um padrão inventado para a aula. O MVVM com fluxo unidirecional de dados é a arquitetura recomendada oficialmente pelo Google no guia de arquitetura de apps Android — a mesma referência que empresas usam para estruturar aplicativos em produção.

A stack que estamos usando é a combinação padrão do desenvolvimento Android atual:

  • Jetpack Compose — o kit de UI recomendado pelo Google para novos apps, substituindo os layouts em XML.
  • ViewModel + Coroutines — parte do conjunto Jetpack, mantido pelo próprio Google.
  • Retrofit — biblioteca de rede consolidada há anos como padrão de fato no ecossistema Android.

Na prática, isso significa que um processo seletivo para vaga Android provavelmente vai perguntar sobre: separação de camadas, por que o ViewModel sobrevive à rotação, o que acontece se você chamar rede na Main Thread, e como você representa estados de tela. Todos esses pontos estão neste projeto.

Para onde isso cresce

O que construímos aqui é a base sólida — mas propositalmente enxuta. Em projetos maiores, três peças costumam entrar em cima dessa mesma estrutura, sem derrubar nada do que você já escreveu:

  • Repository — uma camada entre o ViewModel e as fontes de dados, para quando existir mais de uma origem (rede + banco local, por exemplo).
  • Room — banco de dados local, permitindo que o app funcione offline com os dados já baixados.
  • Injeção de dependência (Hilt/Koin) — para montar automaticamente as dependências entre as camadas, em vez de instanciá-las na mão.
Repare no ganho da arquitetura: nenhuma dessas três adições exigiria reescrever a tela ou o modelo de dados. Elas se encaixam entre as camadas existentes. Um projeto sem separação clara não teria essa flexibilidade — cada nova peça obrigaria a mexer em tudo.

Consumindo uma API REST com Retrofit e Coroutines

Nossa Pokédex busca os dados na PokéAPI, um serviço público e gratuito. O endereço que vamos usar é:

GET 
https://pokeapi.co/api/v2/pokemon/bulbasaur
https://pokeapi.co/api/v2/pokemon/1

Repare que os dois endereços funcionam: a PokéAPI aceita tanto o nome quanto o número do Pokémon no mesmo lugar da URL. É por isso que nosso campo de busca aceita os dois sem precisar de lógica extra.

O que significa "API REST"

Uma API é um conjunto de endereços que um servidor disponibiliza para outros programas consultarem — diferente de um site, que devolve páginas para humanos lerem, uma API devolve dados brutos para programas processarem.

REST é o estilo mais comum de organizar esses endereços. Ele usa os próprios verbos do protocolo HTTP para indicar a intenção:

VerboSignificadoExemplo
GETBuscar dados (não altera nada no servidor)Consultar um Pokémon
POSTCriar um registro novoCadastrar um usuário
PUT / PATCHAtualizar um registro existenteEditar um perfil
DELETERemover um registroExcluir uma postagem

Nosso app usa apenas GET, porque só consulta dados — a PokéAPI é somente leitura. É por isso que a anotação no código é @GET.

Como conferir o que a API devolve, antes de escrever código: abra https://pokeapi.co/api/v2/pokemon/1 direto no navegador. Você verá o JSON cru — a mesma estrutura que suas data class precisam espelhar. Esse é o primeiro passo ao integrar qualquer API nova: olhar a resposta real antes de modelar as classes.

Por que usar Retrofit em vez de fazer na mão

É perfeitamente possível fazer uma requisição HTTP em Android sem nenhuma biblioteca, usando as classes nativas do Java. O problema é a quantidade de trabalho manual: abrir a conexão, definir o método, ler a resposta byte a byte, converter para texto, converter o texto em objetos, fechar a conexão, tratar cada tipo de falha — e repetir tudo isso a cada endpoint novo.

TarefaNa mãoCom Retrofit
Montar a URL com parâmetrosConcatenar strings manualmenteAnotação @Path / @Query
Ler a respostaAbrir stream, ler, fecharAutomático
Converter JSON em objetosPercorrer o JSON campo a campoGSON faz sozinho
Executar fora da Main ThreadCriar e gerenciar threadssuspend fun resolve

Além de reduzir código, isso reduz bugs: cada linha de conversão manual de JSON é uma chance de erro de digitação que só aparece em tempo de execução.

A Main Thread e o congelamento do app

O Android reserva a Main Thread (ou UI Thread) exclusivamente para desenhar a interface — 60 a 120 vezes por segundo. Se uma requisição de rede for disparada nessa linha, tudo trava enquanto o servidor não responde, e o Android mata o app com o erro ANR (App Not Responding).

Isso não é um detalhe teórico: o sistema operacional realmente proíbe essa operação. Tentar fazer rede na Main Thread lança uma exceção chamada NetworkOnMainThreadException — o Android prefere derrubar o app a deixar a interface congelada.

A solução: funções suspend

Marcamos a função de rede com o modificador suspend. Isso diz ao Kotlin que ela pode ser "pausada" enquanto espera a resposta, liberando a Main Thread para continuar desenhando a tela. O Retrofit cuida automaticamente de executar a chamada em segundo plano — não precisamos escrever Dispatchers.IO manualmente, porque ele já faz isso por baixo dos panos.

Coroutine não é o mesmo que thread: criar uma thread é caro para o sistema — cada uma consome memória própria. Coroutines são muito mais leves: milhares delas podem rodar sobre uma quantidade pequena de threads reais, porque quando uma "pausa" esperando a rede, a thread é liberada para outra tarefa em vez de ficar parada. É por isso que o Kotlin adotou esse modelo em vez de expor threads diretamente.
Onde a Coroutine começa: uma função suspend só pode ser chamada de dentro de outra função suspend ou de um escopo de Coroutine. No nosso app, esse ponto de partida é o viewModelScope.launch { } dentro do ViewModel — você vai ver isso no Passo 3.

Passo 1 — O Modelo de Dados 1 de 6

Local: pacote model  |  Arquivo: Pokemon.kt

Estas data class são o "molde" que o Retrofit usa para transformar o JSON da API em objetos Kotlin. Cada propriedade corresponde a um campo da resposta.

model/Pokemon.kt 
package com.seunome.pokedexnovo.model

import com.google.gson.annotations.SerializedName

data class PokemonDetailResponse(
    val id: Int,
    val name: String,
    val sprites: PokemonSprites
)

data class PokemonSprites(
    @SerializedName("front_default") val frontDefault: String?,
    val other: PokemonOtherSprites?
)

data class PokemonOtherSprites(
    val showdown: PokemonShowdownSprites?
)

data class PokemonShowdownSprites(
    @SerializedName("front_default") val frontDefault: String?
)
Para que serve o @SerializedName? No JSON, o campo se chama front_default (com underscore), mas em Kotlin usamos frontDefault (padrão camelCase). Essa anotação faz a ponte entre os dois nomes. Quando o nome é igual nos dois lados — como id e name — o GSON conecta sozinho e a anotação não é necessária.
Por que tantos níveis aninhados? Porque o JSON da PokéAPI é assim: a imagem animada fica em sprites.other.showdown.front_default. Cada nível do JSON vira uma data class. Os ? indicam que o campo pode vir vazio — nem todo Pokémon tem sprite animado, e nesse caso usaremos a imagem estática como reserva.

Passo 2 — A Camada de Rede 2 de 6

Local: pacote network  |  Arquivo: PokeApiService.kt

network/PokeApiService.kt 
package com.seunome.pokedexnovo.network

import com.seunome.pokedexnovo.model.PokemonDetailResponse
import retrofit2.Retrofit
import retrofit2.converter.gson.GsonConverterFactory
import retrofit2.http.GET
import retrofit2.http.Path

interface PokeApiService {
    @GET("pokemon/{nameOrId}")
    suspend fun getPokemon(@Path("nameOrId") nameOrId: String): PokemonDetailResponse
}

object RetrofitClient {
    private const val BASE_URL = "https://pokeapi.co/api/v2/"

    val apiService: PokeApiService by lazy {
        Retrofit.Builder()
            .baseUrl(BASE_URL)
            .addConverterFactory(GsonConverterFactory.create())
            .build()
            .create(PokeApiService::class.java)
    }
}
Você escreveu uma interface, não uma classe. Repare que a função getPokemon não tem corpo — não existe nenhum código dizendo como fazer a requisição. Quem escreve essa implementação é o próprio Retrofit, em tempo de execução, lendo as anotações @GET e @Path. Você só declara o que quer; a biblioteca resolve o como.
Como {nameOrId} vira parte da URL: o trecho entre chaves em @GET("pokemon/{nameOrId}") é um espaço reservado. A anotação @Path("nameOrId") no parâmetro diz ao Retrofit para substituí-lo pelo valor recebido. Chamar getPokemon("pikachu") gera a URL .../pokemon/pikachu.
Por que by lazy? Construir um cliente Retrofit tem custo (configura conversores, timeouts, conexões). O by lazy garante que isso aconteça só na primeira vez que apiService for usado, e todas as chamadas seguintes reaproveitam a mesma instância — em vez de montar um cliente novo a cada busca.

Passo 3 — O ViewModel 3 de 6

Local: pacote viewmodel  |  Arquivo: PokedexViewModel.kt

viewmodel/PokedexViewModel.kt 
package com.seunome.pokedexnovo.viewmodel

import androidx.compose.runtime.getValue
import androidx.compose.runtime.mutableStateOf
import androidx.compose.runtime.setValue
import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import com.seunome.pokedexnovo.model.PokemonDetailResponse
import com.seunome.pokedexnovo.network.RetrofitClient
import kotlinx.coroutines.launch

sealed interface PokedexUiState {
    object Loading : PokedexUiState
    data class Success(val pokemon: PokemonDetailResponse) : PokedexUiState
    object NotFound : PokedexUiState
}

class PokedexViewModel : ViewModel() {

    var uiState: PokedexUiState by mutableStateOf(PokedexUiState.Loading)
        private set

    private var currentId = 1

    init {
        buscar(currentId.toString())
    }

    fun buscar(termo: String) {
        if (termo.isBlank()) return
        viewModelScope.launch {
            uiState = PokedexUiState.Loading
            uiState = try {
                val pokemon = RetrofitClient.apiService.getPokemon(termo.lowercase())
                currentId = pokemon.id
                PokedexUiState.Success(pokemon)
            } catch (e: Exception) {
                PokedexUiState.NotFound
            }
        }
    }

    fun anterior() {
        if (currentId > 1) buscar((currentId - 1).toString())
    }

    fun proximo() {
        buscar((currentId + 1).toString())
    }
}
Por que uma sealed interface em vez de variáveis soltas? A alternativa ingênua seria ter isLoading: Boolean, naoEncontrado: Boolean e pokemon: Pokemon? ao mesmo tempo. Isso permite combinações sem sentido — como isLoading = true e naoEncontrado = true simultaneamente. Com uma sealed interface, a tela está sempre em exatamente um desses três estados, e o Kotlin obriga o when a tratar todos eles. Estados impossíveis simplesmente não compilam.
O que private set faz: permite que qualquer um leia o uiState, mas só o próprio ViewModel pode alterá-lo. É o que impede a tela de mudar o estado por conta própria — exatamente a regra do fluxo unidirecional (o evento sobe, o estado desce).
Por que viewModelScope e não outro escopo? Toda Coroutine iniciada aí é cancelada automaticamente quando o ViewModel é destruído. Se o usuário fechar a tela no meio de uma busca, a requisição é interrompida sozinha — sem isso, ela continuaria rodando e tentaria atualizar uma tela que não existe mais.
O que o init { } faz: é executado uma única vez, quando o ViewModel é criado. É por isso que o app já abre mostrando o Pokémon nº 1, sem o usuário precisar buscar nada.
Por que currentId é atualizado dentro do try: ele só muda depois que a busca deu certo. Assim, se o usuário digitar algo inválido, os botões Prev/Next continuam navegando a partir do último Pokémon que realmente existiu.

                Text(
                    "${pokemon.id} - ${pokemon.name.replaceFirstChar { it.uppercase() }}",
                    style = MaterialTheme.typography.titleLarge
                )
            }
        }

        Spacer(Modifier.height(24.dp))

        OutlinedTextField(
            value = termoBusca,
            onValueChange = { termoBusca = it },
            label = { Text("Name or Number") },
            singleLine = true,
            keyboardOptions = KeyboardOptions(imeAction = ImeAction.Search),
            keyboardActions = KeyboardActions(onSearch = { viewModel.buscar(termoBusca) }),
            modifier = Modifier.fillMaxWidth()
        )

        Spacer(Modifier.height(24.dp))

        Row(horizontalArrangement = Arrangement.spacedBy(16.dp)) {
            Button(onClick = { viewModel.anterior() }) { Text("Prev <") }
            Button(onClick = { viewModel.proximo() }) { Text("Next >") }
        }
    }
}
O operador ?: (Elvis) na escolha da imagem: a linha other?.showdown?.frontDefault ?: sprites.frontDefault significa "use o sprite animado; se ele não existir, use o estático". Os ?. evitam o app quebrar quando algum nível do JSON vier vazio.
Por que remember no campo de busca? A função PokedexScreen é reexecutada toda vez que a tela precisa ser redesenhada (isso se chama recomposição). Sem o remember, a variável termoBusca seria recriada como texto vazio a cada redesenho, e o que o usuário digitou sumiria da tela.
Diferença entre remember e o ViewModel: o texto sendo digitado é um estado temporário da tela — pode se perder na rotação sem prejuízo. Já o Pokémon carregado é um estado da aplicação, que vale a pena preservar. Por isso um fica no remember e o outro no ViewModel.
O que ImeAction.Search faz: troca a tecla "Enter" do teclado do celular por uma tecla de lupa/busca. O KeyboardActions(onSearch = ...) define o que acontece ao pressioná-la — no caso, dispara a busca sem precisar de um botão separado.

Agora que tudo funciona, vamos encaixar o app dentro da ilustração da Pokédex. As constantes no topo são as coordenadas reais da imagem, medidas em porcentagem — é isso que faz o Pokémon cair exatamente sobre a grama.

ui/PokedexScreen.kt 
package com.seunome.pokedexnovo.ui

import androidx.compose.foundation.Image
import androidx.compose.foundation.background
import androidx.compose.foundation.layout.*
import androidx.compose.foundation.text.KeyboardActions
import androidx.compose.foundation.text.KeyboardOptions
import androidx.compose.material3.*
import androidx.compose.runtime.*
import androidx.compose.ui.Alignment
import androidx.compose.ui.Modifier
import androidx.compose.ui.graphics.Color
import androidx.compose.ui.layout.ContentScale
import androidx.compose.ui.res.painterResource
import androidx.compose.ui.text.TextStyle
import androidx.compose.ui.text.font.FontWeight
import androidx.compose.ui.text.input.ImeAction
import androidx.lifecycle.viewmodel.compose.viewModel
import coil.compose.AsyncImage
import com.seunome.pokedexnovo.R
import com.seunome.pokedexnovo.viewmodel.PokedexUiState
import com.seunome.pokedexnovo.viewmodel.PokedexViewModel

// Cores retiradas do projeto web original
private val CorTexto = Color(0xFF3A444D)
private val CorBorda = Color(0xFF333333)
private val CorBotao = Color(0xFF444444)

// Coordenadas medidas na imagem pokedex.png (em % da largura/altura)
private const val TELA_ESQUERDA = 0.160f
private const val TELA_TOPO = 0.270f
private const val TELA_LARGURA = 0.588f
private const val TELA_ALTURA = 0.261f
private const val MOLDURA_BASE = 0.628f
private const val MOLDURA_ESQUERDA = 0.080f
private const val MOLDURA_LARGURA = 0.732f

@Composable
fun PokedexScreen(viewModel: PokedexViewModel = viewModel()) {
    var termoBusca by remember { mutableStateOf("") }

    Box(
        modifier = Modifier.fillMaxSize().background(MaterialTheme.colorScheme.background),
        contentAlignment = Alignment.Center
    ) {
        BoxWithConstraints(
            modifier = Modifier.fillMaxHeight().aspectRatio(425f / 637f)
        ) {
            val largura = maxWidth
            val altura = maxHeight

            Image(
                painter = painterResource(id = R.drawable.pokedex),
                contentDescription = null,
                modifier = Modifier.fillMaxSize(),
                contentScale = ContentScale.FillBounds
            )

            // O Pokémon, posicionado sobre a grama
            Box(
                modifier = Modifier
                    .align(Alignment.TopStart)
                    .offset(x = largura * TELA_ESQUERDA, y = altura * TELA_TOPO)
                    .width(largura * TELA_LARGURA)
                    .height(altura * TELA_ALTURA),
                contentAlignment = Alignment.Center
            ) {
                when (val state = viewModel.uiState) {
                    is PokedexUiState.Loading ->
                        Text("Loading...", fontWeight = FontWeight.SemiBold, color = CorTexto)
                    is PokedexUiState.NotFound ->
                        Text("Not found!", fontWeight = FontWeight.SemiBold, color = CorTexto)
                    is PokedexUiState.Success ->
                        AsyncImage(
                            model = state.pokemon.sprites.other?.showdown?.frontDefault
                                ?: state.pokemon.sprites.frontDefault,
                            contentDescription = state.pokemon.name,
                            modifier = Modifier.size(largura * TELA_LARGURA * 0.55f)
                        )
                }
            }

            // Número e nome, na moldura logo abaixo da tela
            Box(
                modifier = Modifier
                    .align(Alignment.TopStart)
                    .offset(x = largura * MOLDURA_ESQUERDA, y = altura * (TELA_TOPO + TELA_ALTURA))
                    .width(largura * MOLDURA_LARGURA)
                    .height(altura * (MOLDURA_BASE - (TELA_TOPO + TELA_ALTURA))),
                contentAlignment = Alignment.Center
            ) {
                val state = viewModel.uiState
                if (state is PokedexUiState.Success) {
                    Text(
                        "${state.pokemon.id} - ${state.pokemon.name.replaceFirstChar { it.uppercase() }}",
                        style = MaterialTheme.typography.titleMedium,
                        fontWeight = FontWeight.SemiBold,
                        color = CorTexto
                    )
                }
            }

            // Campo de busca
            OutlinedTextField(
                value = termoBusca,
                onValueChange = { termoBusca = it },
                label = { Text("Name or Number") },
                singleLine = true,
                textStyle = TextStyle(fontWeight = FontWeight.SemiBold, color = CorTexto),
                keyboardOptions = KeyboardOptions(imeAction = ImeAction.Search),
                keyboardActions = KeyboardActions(onSearch = { viewModel.buscar(termoBusca) }),
                colors = OutlinedTextFieldDefaults.colors(
                    focusedContainerColor = Color.White,
                    unfocusedContainerColor = Color.White,
                    focusedBorderColor = CorBorda,
                    unfocusedBorderColor = CorBorda,
                    focusedLabelColor = CorTexto,
                    unfocusedLabelColor = CorTexto,
                    cursorColor = CorTexto
                ),
                modifier = Modifier
                    .align(Alignment.TopStart)
                    .offset(x = largura * MOLDURA_ESQUERDA, y = altura * 0.68f)
                    .width(largura * MOLDURA_LARGURA)
            )

            // Botões Prev / Next
            Row(
                modifier = Modifier
                    .align(Alignment.TopStart)
                    .offset(x = largura * MOLDURA_ESQUERDA, y = altura * 0.80f)
                    .width(largura * MOLDURA_LARGURA),
                horizontalArrangement = Arrangement.SpaceBetween
            ) {
                Button(
                    onClick = { viewModel.anterior() },
                    colors = ButtonDefaults.buttonColors(
                        containerColor = CorBotao, contentColor = Color.White
                    )
                ) { Text("Prev <", fontWeight = FontWeight.SemiBold) }

                Button(
                    onClick = { viewModel.proximo() },
                    colors = ButtonDefaults.buttonColors(
                        containerColor = CorBotao, contentColor = Color.White
                    )
                ) { Text("Next >", fontWeight = FontWeight.SemiBold) }
            }
        }
    }
}
O que é BoxWithConstraints: um contêiner que informa ao código o seu próprio tamanho, através de maxWidth e maxHeight. Sem ele, não teríamos como calcular "16% da largura" — pois o app não saberia qual é a largura disponível. É o que faz o layout funcionar em telas de tamanhos diferentes.
Por que aspectRatio(425f / 637f): esses são a largura e a altura reais do arquivo pokedex.png. Travar essa proporção impede que a ilustração seja esticada em telas mais estreitas ou largas — sem isso, a lente redonda da Pokédex aparece achatada.
Por que offset e não padding: o padding empurra um elemento a partir da borda do anterior, acumulando distâncias. O offset posiciona a partir de um ponto fixo — que é o comportamento necessário quando trabalhamos com coordenadas medidas na imagem.
Quer ajustar a posição de algum elemento? Mude os valores das constantes no topo do arquivo. Os números 0.68f (busca) e 0.80f (botões) não vêm da imagem — são posições livres, escolhidas visualmente. Use a aba Split do editor para ver o resultado sem precisar rodar no emulador.

04_troubleshooting.md

Erros Comuns e Como Resolver

Todos os erros abaixo aconteceram de verdade durante a montagem deste projeto. Se algo der errado, procure aqui antes de recomeçar do zero.

requires libraries and applications that depend on it to compile against version 36 (ou 37) or later

O que significa: alguma biblioteca do projeto é mais nova que o compileSdk configurado, e exige um SDK que você provavelmente nem tem instalado.

Solução: confira se o gradle/libs.versions.toml está exatamente como no Passo 0.2. A causa quase sempre é uma versão mais nova que a fixada — especialmente coreKtx, activityCompose ou lifecycleRuntimeKtx.

Por que não simplesmente aumentar o compileSdk: porque isso exige baixar um SDK novo (às vezes ainda em versão Preview) e pode gerar outros conflitos. Fixar bibliotecas estáveis é mais previsível — principalmente numa sala com vários computadores diferentes.

Configuration contains AndroidX dependencies, but the android.useAndroidX property is not enabled

Solução: abra o arquivo gradle.properties (na raiz do projeto, junto do settings.gradle.kts) e adicione a linha:

gradle.properties 
android.useAndroidX=true

Depois clique em Sync Now. Essa linha normalmente já vem no projeto; se sumiu, foi por alguma edição manual do arquivo.

O erro de versão volta mesmo depois de eu corrigir o libs.versions.toml

Causa provável: o Android Studio mostra às vezes uma notificação "Project update recommended — AGP Upgrade Assistant". Se ela for aceita, o assistente reescreve o libs.versions.toml e o build.gradle.kts, desfazendo o que você configurou.

Como identificar: abra o libs.versions.toml e procure por entradas duplicadas, como um coreKtxVersion além do coreKtx, ou uma segunda declaração de core-ktx no bloco [libraries]. Apague as duplicadas.

Se você apagar uma entrada do catálogo, confira se o build.gradle.kts (Module :app) ainda a referencia (ex: uma linha implementation(libs.core.ktx) sobrando) — nesse caso, apague a linha também.

Prevenção: dispense a notificação do Upgrade Assistant quando ela aparecer.

Unresolved reference 'PokedexScreen' (ou o arquivo foi criado dentro de ui/theme)

Causa: o painel do Android Studio agrupa pastas que contêm apenas uma subpasta, exibindo ui.theme em uma linha só. Isso torna fácil criar o arquivo dentro de theme por engano.

Solução: arraste o PokedexScreen.kt da pasta errada para a pasta ui correta. O Android Studio perguntará se deseja atualizar o package — clique em Refactor. Confirme que a primeira linha do arquivo é package com.seunome.pokedexnovo.ui.

Unresolved reference 'PokedexAppTheme' (ou nome de tema parecido)

Causa: o tema gerado pelo template recebe o nome do projeto (um projeto chamado "PokedexAndroid" gera PokedexAndroidTheme). Se você copiar um código que usa outro nome, ele não existe no seu projeto.

Solução: neste guia usamos o MaterialTheme padrão justamente para evitar esse problema. Se preferir usar o tema do seu projeto, abra ui/theme/Theme.kt e confira o nome exato da função antes de usá-la.

O app abre, mas fica sempre em "Not found!"

Causa mais comum: falta a permissão de internet. Confira se a linha <uses-permission android:name="android.permission.INTERNET" /> está no AndroidManifest.xml, acima da tag <application>.

Segunda causa: o emulador está sem conexão. Abra o navegador dentro do emulador e teste qualquer site.

Dica de investigação: troque temporariamente PokedexUiState.NotFound por uma versão que mostre a mensagem real do erro, para saber se é falha de rede ou de conversão do JSON.

ERROR: JAVA_HOME is not set (ao rodar comandos no terminal)

Contexto: acontece ao tentar rodar ./gradlew em um terminal que não conhece o Java embutido no Android Studio.

Solução prática: na maioria dos casos você não precisa do terminal. Se for necessário encerrar processos do Gradle travados, use o Gerenciador de Tarefas do Windows (Ctrl+Shift+Esc), finalize os processos java.exe e reabra o Android Studio.

A imagem da Pokédex aparece esticada ou achatada

Causa: falta travar a proporção da imagem.

Solução: confirme que o BoxWithConstraints do Passo 6 tem o modificador .aspectRatio(425f / 637f). Sem ele, a ilustração é esticada para preencher a tela inteira.

O Pokémon aparece fora da grama (acima, abaixo ou de lado)

Solução: ajuste as constantes TELA_ESQUERDA, TELA_TOPO, TELA_LARGURA e TELA_ALTURA no topo do PokedexScreen.kt. Elas são porcentagens: aumentar TELA_TOPO desce o Pokémon, aumentar TELA_ESQUERDA move para a direita.

Use a aba Split do editor para ver o efeito de cada mudança sem recompilar o app inteiro.
